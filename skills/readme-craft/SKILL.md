# README Craft

The README is your project's landing page. Most readers decide in 30 seconds whether to keep going. Front-load value; defer the encyclopedia.

## When to Activate
- Creating a README for a new project
- Overhauling a README nobody reads
- Reviewing a repo's first impression

## The structure that converts
1. **One-liner** — what it is and who it's for, in a single sentence at the very top. Add a tagline if it helps.
2. **Why / what it solves** — 1–2 sentences or 3 bullets. The reader's problem, not your feature list.
3. **Quickstart** — the fastest path to a working result: install + a copy-pasteable example that actually runs.
4. **A real example** — show input and output, not just API signatures.
5. **Then the details** — configuration, options, API, links to deeper docs.
6. **Footer** — license, contributing, links.

## Rules
- **Show, don't tell.** One runnable example beats three paragraphs.
- **Copy-pasteable commands** in fenced blocks; make sure they work verbatim.
- **Cut the setup friction** — the fewer steps to "it works," the more adoption.
- **Badges sparingly** — build/version/license are useful; a wall of badges is noise.
- **Keep it current** — a wrong example is worse than none; test commands on release.
- **Link out** for depth (full docs, examples dir) instead of bloating the README.

## Smells
- Install instructions below the fold.
- API reference before a single example.
- "Coming soon" sections — delete them.

## Checklist
- [ ] One-line what/who at the top
- [ ] Problem/why before features
- [ ] Quickstart with a runnable, copy-pasteable example
- [ ] Real input→output shown
- [ ] Commands verified; details linked, not dumped
