# UX Writing

Interface copy is part of the UX. Good microcopy is clear, concise, and helps the user act; bad copy confuses, blames, or clutters. Write for the user's task and state of mind.

## When to Activate
- Writing button labels, form fields, tooltips, empty states
- Crafting error, success, or confirmation messages
- Onboarding flows and microcopy

## Principles
- **Clarity over cleverness.** The user is trying to do something — don't make them decode a pun. Plain words win.
- **Be concise.** Cut every word that doesn't help. "Save" not "Click here to save your changes."
- **Action-oriented labels.** Buttons say what happens: "Delete project", "Send invite" — not "OK"/"Submit". The user should predict the result.
- **Speak the user's language**, not the system's. "Couldn't connect" > "Error 502".
- **Consistent terms.** One name per concept across the app (don't mix "folder"/"directory").

## Error messages (the highest-value copy)
A good error says: **what happened, why, and how to fix it** — without blame.
- ❌ "Invalid input."
- ✅ "That email's already in use. Try signing in instead."
- Never blame the user ("you did X wrong"); describe the situation and the next step.

## Empty states
An empty state is an onboarding opportunity, not a dead end. Say what goes here and give the first action: "No projects yet. **Create your first project** to get started."

## Rules
- **Sentence case** for most UI (easier to read than Title Case).
- **Front-load** the important word (users scan).
- **Set expectations** for waits/consequences ("This can't be undone").
- **Voice = consistent** with the brand, but clarity always wins over personality.

## Checklist
- [ ] Buttons/labels describe the action + result
- [ ] Concise; no filler; plain language
- [ ] Errors: what happened + how to fix, no blame
- [ ] Empty states guide to the first action
- [ ] Consistent terminology; sentence case
