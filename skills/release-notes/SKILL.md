# Release Notes

Changelogs are for people deciding *how* to upgrade; release notes are for getting users *excited to* adopt what shipped. They're a mini marketing + enablement doc, not a list of tickets.

## When to Activate
- Announcing a release to users/customers (blog, email, in-app)
- Turning a version's changes into an adoption-driving story

## Structure
1. **Headline** — the single biggest thing, as a benefit. "Export to CSV is here."
2. **Why it matters** — the problem it solves in a sentence.
3. **The highlights** — 2–4 top items, each: what it is + why the user cares + (ideally) a screenshot/gif or a one-line how-to.
4. **Everything else** — a short "Also improved / fixed" list or a link to the full changelog.
5. **Upgrade / next step** — how to get it, and any action required.

## Principles
- **Lead with value, not version numbers.** Users care what they can now *do*, not "v2.4.0".
- **Show, don't tell** — a screenshot/gif of the feature beats three sentences.
- **Prioritize ruthlessly** — highlight the few things that matter; dump the rest in a list. A flat list of 30 items gets skipped.
- **Speak to the user's benefit** ("you can now…"), not your engineering effort.
- **Call out breaking changes / required actions** clearly and early.
- **Match the channel** — punchy for in-app/email, more detail for a blog post.

## Anti-patterns
- Reposting the raw changelog as the announcement.
- Burying the best feature under minor fixes.
- No visual, no "try it" link.

## Checklist
- [ ] Opens with the biggest win as a user benefit
- [ ] 2–4 highlights with why-it-matters + visual/how-to
- [ ] Minor items summarized or linked, not exhaustive
- [ ] Breaking changes / required actions surfaced
- [ ] Clear "how to get it / try it" step
